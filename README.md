# Zapshop Garage — ТЗ MVP мобильного приложения

## 1) Цель продукта
Zapshop Garage — мобильное приложение для владельцев авто (в приоритете авто из США), которое объединяет:
- личный гараж;
- историю обслуживания;
- напоминания о ТО;
- AI-помощника (ChatGPT API);
- маркет б/у запчастей Zapshop;
- подбор деталей по VIN / марке / модели / поколению;
- заявки и заказы.

Ключевая идея: пользователь ведет полный жизненный цикл автомобиля в одном приложении — от учета обслуживания до покупки подходящей детали.

## 2) Платформа и стек

### Мобильное приложение
**Рекомендуется:** Flutter (Android + iOS, единая кодовая база, быстрый UI/UX).

**Альтернатива:** React Native.

### Backend
Запрещено прямое подключение приложения к MySQL/phpMyAdmin.

Правильная схема:
`Mobile App -> Backend/WordPress REST API -> WordPress DB (Zapshop)`

MVP-стек:
- Flutter;
- WordPress REST API (плагин `parts-market-mvp`);
- OpenAI API;
- Telegram Bot API.

## 4) Интеграция с Zapshop API
Базовый URL:
`https://zapshop.by/wp-json/pmm/v1`

### Обязательные endpoint’ы MVP
- `GET /parts` — каталог, поиск, листинг, фильтры.
- `GET /parts/{id}` — карточка товара.
- `GET /parts/match-car` — товары под авто пользователя.
- `GET /filters` — динамические фильтры (марка/модель/поколение/деталь).
- `GET /parts/{id}/check-fitment` — проверка совместимости.
- `POST /requests` — заявка на подбор.

### Примеры ключевых запросов
- Поиск: `/parts?search=фара&page=1&per_page=20`
- По авто: `/parts?brand=Kia&model=K5&generation=DL3`
- Под авто пользователя: `/parts/match-car?brand=Kia&model=K5&generation=DL3`
- OEM: `/parts?oem=92101`
- Цена: `/parts?min_price=100&max_price=500`
- С фото: `/parts?with_photo=1`
- Сортировка: `/parts?sort=price_asc` / `/parts?sort=price_desc`

## 5) Бизнес-правила совместимости (критично)
Приложение и AI **не должны** обещать «100% подходит», если нет финальной проверки.

Допустимые статусы:
- Подходит по основной модели
- Подходит по применяемости
- OEM совпадает
- Возможно подходит
- Нужно проверить VIN/OEM
- Совместимость не подтверждена

Обязательный дисклеймер в карточке товара:
> Перед покупкой обязательно сверим совместимость по VIN/OEM, комплектации и фото старой детали.

## 6) Маркет: обязательные экраны MVP

### 6.1 Главный экран маркета
- Поиск по названию/OEM;
- быстрые категории (двигатели, коробки, фары, бамперы и т.д.);
- блок «Запчасти под мой автомобиль»;
- блоки «Новые поступления», «Популярные категории», «Недавно просмотренные», «Избранное».

### 6.2 Список «Запчасти под моё авто»
Источник: `GET /parts/match-car` по данным из гаража (brand/model/generation/year/engine).

Фильтры:
- категория;
- цена;
- с фото;
- OEM;
- сортировка.

### 6.3 Карточка товара в списке
- фото (или заглушка «Фото скоро будет»);
- название;
- цена (если пусто — «Цена по запросу»);
- склад/адрес;
- статус совместимости;
- кнопки: «Подробнее», «В избранное», «Спросить AI».

### 6.4 Экран карточки товара
Поля:
- галерея;
- название/цена/валюта;
- адрес;
- марка/модель/поколение;
- OEM;
- применяемость;
- блок проверки совместимости;
- AI-подсказка перед покупкой.

Кнопки:
- Купить/Оформить заказ
- Оставить заявку
- Спросить AI
- Позвонить
- Написать в Telegram
- Открыть на сайте
- Добавить в избранное

## 7) AI + маркет (tool-calling через backend)
Нужно реализовать backend-функции:
1. `search_market_parts`
2. `get_market_part_details`
3. `check_market_part_fitment`
4. `create_part_request`

Правило AI-ответов:
- не утверждать «точно подойдет»;
- всегда просить VIN/OEM, сторону, комплектацию, тип оптики/разъема и т.п.;
- если товара нет — предлагать заявку на подбор.

## 8) Локальная БД приложения (минимум)
Таблицы:
- `users`
- `cars`
- `service_records`
- `service_reminders`
- `favorites`
- `cart`
- `cart_items`
- `orders`
- `order_items`
- `chat_messages`

Важно:
- в `favorites` хранить `part_id` из Zapshop API;
- каталог запчастей **не дублировать** целиком в локальной БД на MVP.

## 9) Корзина и заказы
На MVP заказ = заявка менеджеру (без онлайн-оплаты).

Перед подтверждением заказа обязательно показывать предупреждение:
> Перед подтверждением заказа менеджер проверит совместимость детали по VIN/OEM.

Статусы заказа:
- Новый
- В обработке
- Проверяем совместимость
- Ожидает подтверждения
- Забронирован
- Оплачен
- Отправлен
- Закрыт
- Отменён

## 12) Что НЕ входит в MVP

- сложный VIN-декодер;
- OBD-сканер;
- маркетплейс СТО;
- распознавание повреждений по фото;
- сложная CRM;
- полноценная логистика;
- автоматическое 100% определение совместимости.

## 13) Ключевой пользовательский сценарий
1. Пользователь добавляет авто в гараж.
2. Приложение предлагает «Запчасти под моё авто» через `GET /parts/match-car`.
3. Пользователь открывает карточку.
4. Выполняется `GET /parts/{id}/check-fitment`.
5. Отображается «нужно подтвердить по VIN/OEM».
6. Пользователь оформляет заказ/заявку.
7. Менеджер валидирует и подтверждает.

## Коротко для разработчика
Сделать Flutter-приложение (iOS/Android) с модулями гаража, ТО, напоминаний, AI-чата и маркета Zapshop.
Данные маркета получать по REST API Zapshop (`/parts`, `/parts/{id}`, `/parts/match-car`, `/filters`, `/parts/{id}/check-fitment`, `/requests`).
AI работает через backend-функции, помогает с подбором и рисками, но не обещает 100% совместимость без VIN/OEM-проверки.

## 14) Монетизация в будущих версиях
После MVP запланировать модель монетизации приложения:

- **Платная подписка (Premium):**
  - расширенные AI-консультации;
  - расширенная история обслуживания и аналитика расходов;
  - приоритетный подбор запчастей;
  - дополнительные уведомления и персональные рекомендации.

- **Реклама в приложении:**
  - рекламные блоки в ленте маркета и на главном экране;
  - промо-позиции товаров/партнеров;
  - аккуратная интеграция без ухудшения основного UX.

Принцип: в MVP фокус на полезности и стабильности продукта, монетизацию (подписка + реклама) внедрять поэтапно в следующих релизах.
